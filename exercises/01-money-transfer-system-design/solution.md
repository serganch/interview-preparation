# Объем полезных данных

Исходные требования:

- 10 млн пользователей
- 1 млн переводов в сутки
- хранить историю за 7 лет (~2500 дней)

Что можно вывести:
- 1 млн переводов в сутки * 2500 дней = 2.5 млрд переводов за всю историю
- 1 перевод содержит историю из 3 элементов максимум (ACCEPTED -> PROCESSING -> COMPLETED/CANCELLED/FAILED)
- Каждый перевод содержит id (предположим 64 битное число - 8 байт), от кого/кому (32 бита * 2 = 8 байт), сумму (строка с десятичным числом до 20 ASCII/UTF-8 символов/цифр с точкой - в среднем 8 байт), таймстамп размещения (8 байт), таймстамп последнего обновления (8 байт). Итого: 40 байта
- Каждая запись истории перевода содержит статус (1 байт), таймстамп (8 байт). Итого: 9 байт
- Таким образом объем данных по одному переводу: 40 байт + 3 * 9 байт = 67 байт. Округлим до 70
- Таким образом объем данных по всем переводам: 2.5 млрд переводов * 70 байт = 18 ГБ

Почему сумму перевода храним в строке. Для удобства и унификации. 
Нам не нужно выполнять математические операции над суммами (во всяком случае на уровне БД). У суммы, выраженной строкой, нет максимального значения. 
Строка дает в будущем возможность работы с разными валютами и разным количеством цифр после запятой.

Итого целевой объем данных: 18 ГБ без учета индексов, избыточности хранения и ссылочной информации

Причем это данные, к которым нужен быстрый доступ.

# Объем входящего/исходяещего трафика

1 запрос на отправку перевода - примерно 100 байт. 100*12.5 = 1250 байт в секунду на входе
1 запрос на получение истории перевода - 10000 байт (100 записей по 100 байт). 10000*125 = 1250000 байт в секунду на выходе
1 запрос на получение детализации перевода - 1000 байт. Запрос относительно редкий. Допустим 1 раз в секунду.

Итого имеем в среднем 1500-2000 байт в секунду на входе и 1500000 байт в секунду на выходе. Даже с учетом возможных пиков это несущественные объемы трафика
Внутри периметра системы объемы полезного трафика примерно те же.

# Общая схема решения

## Ключевые архитектурные решения

### Данные
Объем хранимых полезных данных оценивается в сотни гигабайт, что позволяет хранить все в одной синхронно реплицируемой SQL БД.

Для сущности переводов в рамках системы заводим отдельный суррогатный id. Дело в том, что жизненный цикл ордера в системе шире, чем перевода у банковского провайдера.
Ордер системы создается раньше перевода в провайдере со специальным статусом `pending` и до того, как будет известен id перевода провайдера.

#### Таблица ордеров
Объем полезных данных по ордерам равен примерно (100 байт на запись * 2.5 млрд = 250 ГБ)
Добавим индексы, и, грубо, имеем 500 ГБ. 2.5 млрд записей вполне терпимо для современной SQL БД типа Postgres. 

таблица orders:

- order_id (PK, автоинкремент),
- transfer_id (null пока не создан трансфер),
- from_user_id, 
- to_user_id, 
- created_at,
- updated_at,
- status (pending \[default], accepted, pricessing, completed, cancelled, failed), 
- amount
- idempotency_key (BIGINT, nullable) ключ идемпотентности для избежания случайного повторного создания ордера, очищается после создания трансфера

Индексируем order_id, transfer_id, from_user_id, to_user_id, created_at, status.

Индекс по created_at может быть использован для удаления устаревших данных (> 7 лет).

частичный индекс по order_id где `transfer_id is null` -- transactional outbox
частичный unique индекс по idempotency_key где `idempotency_key is not null`

Мы не знаем точно, сколько по времени в среднем занимает путь перевода от начального состояния до конечного. Предположим, в среднем 1 минута.
Тогда объем данных по всем незавершенным переводам будет равен в среднем примерно 700 (12*60) записей по 50 байт с пиками до 12000 (200*60) записей.
Даже если время обработки переводов растянется на минуты, вряд ли количество элементов в индексе outbox превысит несколько сотен тысяч.
Если размер индекса превысит некий конфигурируемый предел, создание переводов прекращается с возвращением ошибки.

В случае Postgres с таблицей через триггер ON CREATE связан канал pub sub, через который Workers реагируют на создание ордеров.
Если Postgres по каким-то причинам не может быть использован, для механизма pub/sub можно использовать Redis. Смысла в использовании персистентной очереди нет, так как все события в очереди восстанавливаемы из БД.

#### Таблица истории статусов ордеров
Размер хранимых данных ~30 байт * 2.5 млрд переводов = 75 ГБ. С покрывающим индексом по order_id и updated_at, таблица займет не более 150 ГБ.

таблица order_history (в случае SQL)

- order_id (PK)
- updated_at (PK)
- status

Индекс PK может быть использован для удаления устаревших данных (> 7 лет).

### Прочее
- Объем сетевого трафика незначителен, нотификаций со стороны сервера не требуется, поэтому можно ориентироваться на односторонее REST API с JSON payload
- Нет смысла делать сложную микросервисную архитектуру, поскольку бизнес-логика относительно простая.

Таким образом в системе можно выделить следующие компоненты:

- REST API Gateway.
- Workers для фоновой отслеживания состояния ордеров и реализации transactional outbox создания ордеров.
- SQL хранилище ордеров.

# Компоненты системы

## Внешние компоненты

### Банковский провайдер

Предлагает REST API вида

`POST /transfers` - размещает ордер на перевод от пользователя с id `sender_id` пользователю с id `receiver_id` на сумму `amount`. Гарантирует не более 50 RPS. 
Предполагается, что вызов идемпотентен через заголовок `Idempotency-Key`.

`GET /transfers/{transfer_id}` - возвращает перевод с id `transfer_id` со статусом и историей изменения.

Возможные статусы:
• ACCEPTED — запрос принят нашей системой;
• PROCESSING — операция передана провайдеру и ещё не завершена;
• COMPLETED — перевод успешно завершён;
• FAILED — перевод завершился неуспешно;
• CANCELLED — перевод отменён.

Также провайдер может дернуть webhook при изменении статуса ордера. Гарантии отсутствуют (может быть вызван несколько раз по одному событию, а может не быть вызван вообще) 

### Система управления пользователями

Предлагает REST API вида

`GET /users/{user_id}` - возвращает пользователя с id `user_id` и со статусом.
`GET /users?user_ids={user_ids}` - возвращает информацию по нескольким пользователям.

Возможные статусы:
• ACTIVE — пользователь активен;
• BLOCKED — пользователь заблокирован.

## Внутренние компоненты

### API Gateway

Реализует внешнее REST API для взаимодействия с клиентскими приложениями (как web, так и мобильными).

`POST /orders` - размещение ордера на перевод с указанием sender_id и receiver_id. Принимает заголовок `Idempotency-Key` для идемпотентности.

Проверяет валидность суммы (неотрицательное число с точкой, на соответствие балансу не проверяем). 
Синхронно выполняет запросы к системе управления пользователями на предмет активности и валидности id. 
Будет неплохо, если сервис пользователей сможет отдать информацию по обоим пользователям в одном запросе (`GET /users?user_ids=13,25`).
Если не может, два запроса делаются параллельно. В случае отсутствия какого-либо из пользователей или блокировки любого из них возвращает 400.
После валидации пользователей атомарно создает запись в таблице orders с ключом идемпотентности и со статусом pending.


`GET /orders/{order_id}` - возвращает ордер с id `order_id` со статусом и историей изменения. Делает запрос в order_history


`GET /history?user_id={user_id}&from_ts={from_ts}&to_ts={to_ts}&order_statuses={order_statuses}&page={page}&page_limit={page_limit}` - возвращает историю переводов пользователя с id `user_id` за период.
Делает запрос с соответствующими параметрами в orders.


Характеристики:
- stateless
- выполняется в нескольких инстансах с автоматической балансировкой на входе для failover и распределения нагрузки

### Worker для обработки PENDING ордеров

Подписан на создание записи в orders. Выполняет запрос на создание трансфера у провайдера.
После успешного выполнения выставляет статус записи в соответствии с тем, что вернул провайдер.
При неуспешном переводит статус записи в failed.
В обоих случаях обновляет историю order_history

Этот же компонент в фоне (раз в 10 минут) выполняет задачу по обновлению статуса ордеров, которые не были еще финализированы (status == ACCEPTED || PROCESSING) (выборка из orders FOR UPDATE SKIP LOCKED) 
и обновлялись (updated_at) ранее чем 10 минут назад. Нужна как защита от несрабатывания веб-хука. По всем найденным записям worker с некоторым фактором параллелизации опрашивает провайдера через
`GET /transfers/{transfer_id}`. Получив данные, обновляет status, updated_at и order_history. При получении 404 запись переводится в failed. При 5xx пропускаем и делаем повторную попытку при следующем запуске задачи.

- выполняется в нескольких инстансах в зависимости от нагрузки в режиме work stealing (FOR UPDATE SKIP LOCKED)
- инстанс для фоновой задачи выбирается через Consul или Zookeeper или через распределенный lock в Redis

### web-hook host

Обслуживает эндпойнт веб-хука от провайдера. Принимает сигналы по изменению статуса трансфера. 
Находит запись в orders по transfer_id и обновляет статус записи в соответствии с тем, что вернул провайдер. Обновляет историю order_history

# Гарантии

- Корректность данных обеспечивается через идемпотентность и периодическую синхронизацию данных из провайдера
- Поскольку все клиентские запросы финализируются в БД, SLA и масштабирование обеспечивается репликацией всех компонент, включая RO реплики БД
